    8. Authentifizierung und Autorisierung

    Bei jedem Request stellen sich zwei getrennte Fragen:

    • Wer ist der Benutzer? Das ist die Authentifizierung: Der Benutzer hat sich mit Benutzername und Passwort identifiziert, und jeder weitere Request muss belegen, dass er von ihm stammt;
    • Darf er auf diese Seite zugreifen? Das ist die Autorisierung: In der Fallstudie verwaltet nur ein Benutzer mit der Rolle ADMIN die Ärzte und Clients.

    Der Identitätsnachweis muss jeden Request begleiten. [Django] besitzt eine vollständige Authentifizierungsanwendung, [django.contrib.auth]: ein Modell [User] (eine Datenbanktabelle), eine Middleware, die den angemeldeten Benutzer in [request.user] ablegt, Login- und Logout-Views, Berechtigungen, Gruppen und die Administrationsoberfläche, die sie verwaltet. Sie speichert den angemeldeten Benutzer in seiner Session (siehe das Kapitel über Gültigkeitsbereiche), was für eine Webanwendung die einfachste Lösung ist. Die Fallstudie dagegen verwendet in allen ihren Versionen ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel], [Symfony]) ein JWT-Token (JSON Web Token), das wir auch hier einsetzen: Nach dem Login erzeugt der Server ein Token, das die Identität des Benutzers enthält, und signiert es mit einem geheimen Schlüssel (das ist das Prinzip des signierten Cookies in Beispiel 23). Das Token wird in einem Cookie gespeichert; der Browser sendet es bei jedem Request zurück; der Server prüft die Signatur. Der Benutzer kann sein Token lesen, aber nicht verändern: Jede Änderung macht die Signatur ungültig. Das Format ist standardisiert (RFC 7519), wird von allen Programmiersprachen verstanden, und das Token enthält sein Ablaufdatum. Vor allem muss der Server nichts speichern: Jeder Server, der den Schlüssel kennt, kann das Token prüfen.

    Die Benutzer der Fallstudie stehen in einer eigenen Tabelle, [users], und nicht in [django.contrib.auth]; die Token selbst haben in [django.contrib.auth] keinen Platz. Wir setzen die Authentifizierung daher selbst um, mit Werkzeugen, die wir bereits kennen, was den Vorteil hat, dass alles transparent bleibt:

    • Eine Middleware (Beispiel 03) bestimmt bei jedem Request anhand des Tokens in seinem Cookie, wer der Benutzer ist, und legt ihn im Request ab ([request.user], Beispiel 12). Der Rest der Anwendung sieht nur dieses Ergebnis;
    • Dekoratoren (Beispiel 08) schützen die Views: [@login_required], [@role_required("ADMIN")];
    • Passwörter werden mit den Hash-Funktionen von [Django] geprüft ([django.contrib.auth.hashers], die ohne den Rest der Anwendung [auth] verwendet werden können);
    • Zugriffsverweigerungen sind [PermissionDenied]-Exceptions, die von einer View [handler403] in eine Fehlerseite umgewandelt werden (Beispiel 24);
    • Login-Versuche werden mithilfe des Caches von [Django] begrenzt (Beispiel 27).

    Die Erstellung und Prüfung der Token übernimmt die Bibliothek [PyJWT], die in [Python] am häufigsten verwendete, die durch die Beispieldatei [requirements.txt] installiert wird (sie wird unter dem Namen [jwt] importiert). (Es gibt JWT-Token-Bibliotheken für [Django], etwa [djangorestframework-simplejwt], die für APIs gedacht sind; für eine Webanwendung genügen wenige Zeilen, und sie veranschaulichen den Mechanismus besser.)

from dataclasses import dataclass, field


@dataclass(frozen=True)
class User:
    login: str
    name: str
    # die Rolle: USER oder ADMIN
    role: str
    # der HASH des Passworts (leer für einen aus einem Token gelesenen Benutzer)
    password_hash: str = ""
    # der Inhalt des Tokens, das den Benutzer authentifiziert hat; field(default_factory=dict):
    # ein NEUES leeres Dictionary für jedes Objekt
    claims: dict = field(default_factory=dict)


# wir speichern NIEMALS ein Passwort, nur seinen Hash, ein für alle Mal
# von der Funktion make_password von Django berechnet (Algorithmus PBKDF2-SHA256, 1.500.000
# Iterationen, ein zufälliges Salt):
# python -c "from django.conf import settings; settings.configure();
#            from django.contrib.auth.hashers import make_password; print(make_password('marie'))"
USERS = {
    "marie": ("Marie Pélissier", "USER",
              "pbkdf2_sha256$1500000$pjnFn2tL1G4bu5rVFTv6sZ$Y6v+fj3dC+Y0LZYJGxeE1OOi9beaZVuMVm6R6tljEwI="),
    "admin": ("Administrator", "ADMIN",
              "pbkdf2_sha256$1500000$UTT2hXVaLIEAuGHPFxgnv9$D9+Owt9lDG14VrvArR3n0GGQXWjY9Sg8cgFwip4+yx4="),
}


def find(login: str) -> User | None:
    if login not in USERS:
        return None
    # das "Entpacken" eines Tupels: seine drei Elemente in drei Variablen
    name, role, password_hash = USERS[login]
    return User(login, name, role, password_hash)
    • Zeilen 7–17: ein Benutzer: das Login, der Name, die Rolle, der Passwort-Hash und der Inhalt des Tokens, das den Benutzer authentifiziert hat (leer bei einem Benutzer aus der Benutzerliste). Die letzten beiden Attribute haben einen Standardwert. Bei einem Dictionary darf dieser Wert nicht als [claims: dict = {}] geschrieben werden: Dieses Dictionary würde nur einmal erstellt und von allen Objekten geteilt. [field(default_factory=dict)] weist [@dataclass] an, für jedes neue Objekt [dict()] aufzurufen;
    • Zeilen 20–24: Ein Server speichert niemals ein Passwort, auch nicht verschlüsselt: Würde die Datenbank gestohlen, wären auch die Passwörter gestohlen (und viele Menschen verwenden überall dasselbe Passwort). Er speichert das Ergebnis einer Hash-Funktion, einer Einwegfunktion: Man kann den Hash eines Passworts berechnen, aber aus dem Hash nicht auf das Passwort zurückschließen. Um ein eingegebenes Passwort zu prüfen, berechnet man seinen Hash und vergleicht ihn mit dem in der Datenbank gespeicherten;
    • Zeilen 25–30: zwei Testbenutzer, fest im Programm eingetragen (Beispiel 28 und die Fallstudie befüllen damit eine Datenbank): für jedes Login der Name, die Rolle und der Passwort-Hash. Der Hash wurde ein für alle Mal mit der Funktion [make_password] von [Django] berechnet (der Befehl steht in einem Kommentar), und zwar mit dem Standardalgorithmus PBKDF2-SHA256. Der gespeicherte Hash besteht aus vier Teilen, getrennt durch [$]: den Algorithmus ([pbkdf2_sha256]), die Anzahl der Iterationen, das Salt und schließlich das Ergebnis. Ein guter Algorithmus zum Hashen von Passwörtern hat zwei Eigenschaften. Er ist absichtlich langsam, mit einstellbarem Grad der Langsamkeit: PBKDF2 wendet die Funktion SHA-256 1.500.000-mal an, was einige hundert Millisekunden dauert – für einen Benutzer nicht wahrnehmbar, für einen Angreifer, der Milliarden von Passwörtern ausprobieren will, aber sehr kostspielig; [Django] erhöht diese Zahl mit jeder Version, um mit der Rechenleistung Schritt zu halten (seine Anwendung [auth] aktualisiert dann bei Logins die gespeicherten Hashes); ältere Hashes bleiben prüfbar, da sie ihre Iterationszahl enthalten. Er ist gesalzen: Ein zufällig erzeugtes Salt wird vor dem Hashen mit dem Passwort vermischt und im Hash selbst gespeichert; zwei Benutzer mit demselben Passwort haben somit unterschiedliche Hashes. [Django] kann auch [Argon2] und [bcrypt] verwenden (Einstellung [PASSWORD_HASHERS]); die Fallstudie, deren Datenbank [bcrypt]-Hashes enthält, verwendet direkt die Bibliothek [bcrypt];
    • Zeilen 33–38: der Benutzer eines Logins oder [None]. [not in] prüft das Fehlen eines Schlüssels; die Zuweisung [name, role, password_hash = ...] entpackt ein Tupel: Jede Variable erhält das entsprechende Element.

    # security/auth.py: die Prüfung der Passwörter und der JWT-Tokens

import time

import jwt
from django.conf import settings
from django.contrib.auth.hashers import check_password

from . import users
from .users import User

# der Name des Cookies, das das Token trägt
COOKIE = "token"


# der Benutzer oder None, wenn das Login unbekannt oder das Passwort falsch ist.
# check_password hasht das eingegebene Passwort mit dem Salt und dem Algorithmus des gespeicherten
# Hashs und vergleicht dann die beiden Ergebnisse
def validate(login: str, password: str) -> User | None:
    if not login or not password:
        return None
    user = users.find(login)
    if user is None or not check_password(password, user.password_hash):
        return None
    return user


# das JWT-Token des Benutzers, signiert mit dem geheimen Schlüssel (HMAC-SHA256)
def create_token(user: User) -> str:
    now = int(time.time())
    # der Inhalt des Tokens: die "Claims" (Aussagen über den Benutzer)
    claims = {
        "sub": user.login,
        "name": user.name,
        "role": user.role,
        "iat": now,
        "exp": now + settings.JWT_DURATION_MINUTES * 60,
    }
    return jwt.encode(claims, settings.JWT_SECRET, algorithm="HS256")


# der durch ein Token beschriebene Benutzer, dessen Signatur und Ablaufdatum
# gültig sind; sonst None (gefälschtes, abgelaufenes oder unlesbares Token)
def verify(token: str) -> User | None:
    try:
        # decode prüft die Signatur UND das Ablaufdatum (Claim exp)
        claims = jwt.decode(token, settings.JWT_SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return None
    return User(claims["sub"], claims["name"], claims["role"], claims=claims)
    • Zeile 5: die Bibliothek [PyJWT];
    • Zeile 7: die Funktion [check_password] von [Django];
    • Zeile 13: der Name des Cookies, das das Token trägt;
    • Zeilen 19–25: Prüfung von Benutzername und Passwort. [check_password] liest den Algorithmus, die Anzahl der Iterationen und das Salt aus dem gespeicherten Hash, hasht damit das eingegebene Passwort und vergleicht die beiden Ergebnisse (in konstanter Zeit, siehe Beispiel 23). Ein unbekannter Benutzername und ein falsches Passwort liefern dasselbe Ergebnis, [None];
    • Zeilen 29–39: Erzeugung des Tokens. Sein Inhalt ist ein Dictionary mit Claims über den Benutzer. Einige haben standardisierte Namen: [sub] (subject), die Kennung des Benutzers; [iat] (issued at), das Erstellungsdatum; [exp] (expiration), das Ablaufdatum. Die Datumsangaben werden in Sekunden seit dem 1. Januar 1970 ausgedrückt ([time.time()] liefert diese Zahl samt Nachkommastellen, die [int] weglässt). Die übrigen Felder sind optional: hier der Name und die Rolle. [jwt.encode] erzeugt das Token und signiert es mit dem Algorithmus [HS256] (HMAC-SHA256, eine Signatur mit einem gemeinsamen geheimen Schlüssel);
    • Zeilen 44–50: Prüfung des Tokens. [jwt.decode] prüft die Signatur und das Ablaufdatum und gibt dann die Claims zurück. Jede Auffälligkeit (gefälschtes, abgelaufenes oder fehlerhaftes Token) löst eine Exception der Klasse [jwt.InvalidTokenError] oder einer ihrer Unterklassen aus, die der Block [except] abfängt. Der Parameter [algorithms] gibt die Liste der akzeptierten Algorithmen an: Ein Token, das einen anderen Algorithmus (oder gar keinen, [none]) angibt, würde abgelehnt. Das gültige Token wird zu einem [User] ohne Hash, zusammen mit seinen Claims (Parameter namens [claims]).

    # security/middleware.py: AUTHENTIFIZIERUNG: Wer ist bei jeder Anfrage der Benutzer?

from django.shortcuts import redirect

from . import auth


class Authentication:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # standardmäßig ist der Besucher anonym
        request.user = None
        token = request.COOKIES.get(auth.COOKIE)
        if token is not None:
            user = auth.verify(token)
            if user is None:
                # ein ungültiges Token (abgelaufen, gefälscht): weiter nach /login, und wir
                # löschen das Cookie
                response = redirect("login")
                response.delete_cookie(auth.COOKIE)
                return response
            request.user = user
        return self.get_response(request)

    Bei jedem Request, vor der View:

    • Zeile 14: Standardmäßig ist der Besucher anonym: [request.user] ist gleich [None];
    • Zeilen 15–17: Enthält der Request das Token-Cookie, wird das Token geprüft;
    • Zeilen 18–23: ein ungültiges Token (abgelaufen oder gefälscht): Die Middleware antwortet selbst, ohne den Rest der Verarbeitungskette aufzurufen, indem sie auf die Login-Seite umleitet, und nutzt die Gelegenheit, das Cookie zu löschen: [delete_cookie] fügt der Antwort ein leeres, bereits abgelaufenes Cookie hinzu;
    • Zeile 24: ein gültiges Token: Der Benutzer, den es identifiziert, wird im Request abgelegt. Der Benutzer wird nicht in der Benutzerliste nachgeschlagen: Das Token genügt, da es signiert ist.

    Die Middleware verweigert keinen Zugriff: Sie ermittelt, wer der Benutzer ist, oder stellt fest, dass er anonym ist. Das ist die Authentifizierung. Verweigerungen werden von der Zugriffskontrolle behandelt.

    # security/decorators.py: die Zugriffskontrolle der Views

from functools import wraps

from django.shortcuts import redirect


# @login_required: Die View wird nur für einen authentifizierten Benutzer ausgeführt; ein
# anonymer Besucher wird auf die Login-Seite weitergeleitet
def login_required(view):
    @wraps(view)
    def wrapper(request, *args, **kwargs):
        if request.user is None:
            return redirect("login")
        return view(request, *args, **kwargs)
    return wrapper

    Der Dekorator [@login_required] umhüllt eine View (Beispiel 08): Ist der Benutzer anonym, antwortet er mit einer Umleitung auf die Login-Seite, ohne die View aufzurufen; andernfalls ruft er die View auf. [django.contrib.auth] stellt einen Dekorator mit demselben Namen und derselben Aufgabe bereit, [@login_required], der auf seinem eigenen [request.user] beruht.

    # accounts/views.py: Login, Logout und eine Seite, die authentifizierten
# Benutzern vorbehalten ist

from django.conf import settings
from django.shortcuts import redirect, render
from django.views.decorators.http import require_GET, require_http_methods, require_POST

from security import auth
from security.decorators import login_required


@require_GET
def home(request):
    return redirect("profile")


# GET: das Formular; POST: das Login (das Anti-CSRF-Token wurde von
# CsrfViewMiddleware geprüft)
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return render(request, "auth/login.html")
    login = request.POST.get("login", "")
    user = auth.validate(login, request.POST.get("password", ""))
    if user is None:
        # eine absichtlich vage Meldung: Wir sagen nicht, ob es das Login oder das Passwort ist
        return render(request, "auth/login.html",
                      {"login": login, "error": "Incorrect login or password."})
    # das Token in einem Cookie: Das JavaScript der Seite kann es nicht lesen
    # (httponly); es begleitet keine POST-Anfragen von anderen Sites
    # (samesite); es verschwindet zugleich mit dem Ablauf des Tokens (max_age)
    response = redirect("profile")
    response.set_cookie(auth.COOKIE, auth.create_token(user),
                        max_age=settings.JWT_DURATION_MINUTES * 60, httponly=True, samesite="Lax")
    return response


# Logout: nur per POST (ein einfacher Link auf einer anderen Site kann den Benutzer
# nicht ohne sein Wissen abmelden); wir löschen das Cookie
@require_POST
def logout(request):
    response = redirect("login")
    response.delete_cookie(auth.COOKIE)
    return response


# request.user: der authentifizierte Benutzer, von der Middleware gefunden
@require_GET
@login_required

from functools import wraps

from django.core.exceptions import PermissionDenied
from django.shortcuts import redirect


# @login_required: Die View wird nur für einen authentifizierten Benutzer ausgeführt; ein
# anonymer Besucher wird auf die Login-Seite weitergeleitet
def login_required(view):
    @wraps(view)
    def wrapper(request, *args, **kwargs):
        if request.user is None:
            return redirect("login")
        return view(request, *args, **kwargs)
    return wrapper


# @role_required("ADMIN"): ein PARAMETRISIERTER Dekorator (siehe Beispiel 08). Die View wird
# nur ausgeführt, wenn der authentifizierte Benutzer die verlangte Rolle hat; andernfalls erzeugt die
# Exception PermissionDenied eine 403-Antwort (siehe security/errors.py)
def role_required(role):
    def decorator(view):
        @wraps(view)
        @login_required
        def wrapper(request, *args, **kwargs):
            if not request.user.has_role(role):
                raise PermissionDenied(f"role {role} required")
            return view(request, *args, **kwargs)
        return wrapper
    return decorator
    • Zeilen 23–32: ein parametrisierter Dekorator (Beispiel 08), [@role_required("ADMIN")]. Der Wrapper ist selbst von [@login_required] umhüllt: Ein anonymer Besucher wird zuerst auf die Login-Seite geschickt; ein authentifizierter Benutzer, der die verlangte Rolle nicht besitzt, löst die Exception [PermissionDenied] aus (Beispiel 24), was zu einem 403-Fehler (Forbidden) führt.

    Der Unterschied zwischen den beiden Verweigerungsfällen ist bedeutsam: Ein anonymer Besucher, der eine geschützte Seite anfordert, wird auf die Login-Seite umgeleitet; ein authentifizierter Benutzer, der die verlangte Rolle nicht besitzt, erhält einen 403-Fehler – ein erneutes Anmelden wäre zwecklos, da er bereits authentifiziert ist.

def svg(text: str) -> str:
    w, h = WIDTH, HEIGHT
    parts = [f'<svg xmlns="http://www.w3.org/2000/svg" width="{w}" height="{h}" viewBox="0 0 {w} {h}">',
             '<rect width="100%" height="100%" fill="#f5f7fa"/>']
    # die Zeichen: jedes vergrößert, geneigt, verschoben, und jeder Punkt leicht
    # zufällig verschoben
    step = (w - 20) / len(text)
    for i, character in enumerate(text):
        scale = random(4.6, 5.6)    # Größe einer Gittereinheit in Pixeln
        angle = random(-0.35, 0.35)   # Drehung im Bogenmaß (etwa ±20°)
        cx = 10 + step * (i + 0.5) + random(-3, 3)    # Mittelpunkt des Zeichens
        cy = h / 2 + random(-4, 4)
        for stroke in FONT[character]:
            d = []
            # range(0, n, 2): 0, 2, 4 ... ein Punkt = zwei Zahlen
            for k in range(0, len(stroke), 2):
                # Punkt des Rasters, zentriert auf (2, 3), verzerrt, gedreht, platziert
                x = (stroke[k] - 2 + random(-0.2, 0.2)) * scale
                y = (stroke[k + 1] - 3 + random(-0.2, 0.2)) * scale
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
            parts.append(f'<path d="{" ".join(d)}" fill="none" stroke="{color()}" '
                         f'stroke-width="{random(2.2, 3):.1f}" stroke-linecap="round" '
                         f'stroke-linejoin="round"/>')
    # 3 Störstriche: Kurven, die das Bild durchkreuzen
    for _ in range(3):
        parts.append(f'<path d="M{random(0, 20):.1f} {random(5, 45):.1f} '
                     f'C{random(30, 60):.1f} {random(0, 50):.1f} {random(90, 120):.1f} '
                     f'{random(0, 50):.1f} {random(130, 150):.1f} {random(5, 45):.1f}" '
                     f'fill="none" stroke="{color()}" stroke-width="1.3"/>')
    parts.append("</svg>")
    return "".join(parts)

from dataclasses import dataclass

# die Lebensdauer eines Captchas, in Sekunden
LIFETIME = 600


# ein Captcha: seine Kennung und sein Bild (SVG)
@dataclass(frozen=True)
class Captcha:
    id: str
    svg: str


def generate() -> Captcha:
    text = captcha_drawing.random_text(5)
    # eine zufällige, nicht erratbare Kennung: 12 Bytes, von einem
    # kryptografischen Generator gezogen, hexadezimal geschrieben
    id = secrets.token_hex(12)
    # die erwartete Antwort im Cache, für 10 Minuten: Der Cache vergisst sie danach von
    # selbst
    cache.set(f"captcha.{id}", text, LIFETIME)
    return Captcha(id, captcha_drawing.svg(text))


# das Captcha wird in jedem Fall VERBRAUCHT: Ein Bild wird nur einmal verwendet
def verify(id: str, entered: str) -> bool:
    if not id or not entered:
        return False
    # get liefert den Wert oder None; delete entfernt die Antwort aus dem Cache, egal ob sie
    # richtig ist oder nicht
    expected = cache.get(f"captcha.{id}")
    cache.delete(f"captcha.{id}")
    if expected is None:
        return False    # unbekannte Kennung oder abgelaufenes CAPTCHA
    # casefold: der String in Kleinbuchstaben, für einen Vergleich, der die Groß- und Kleinschreibung ignoriert
    return expected.casefold() == entered.strip().casefold()

import time

from django.conf import settings
from django.core.cache import cache


# die Fehlschläge eines Clients werden in einem festen Zeit-FENSTER gezählt: höchstens
# LOGIN_MAX_FAILURES Fehlschläge pro Fenster von LOGIN_WINDOW_SECONDS Sekunden
class Limiter:
    def __init__(self, ip: str):
        self.key = f"login.{ip}"

    # die zu wartenden Sekunden, wenn der Client gesperrt ist, sonst 0
    def wait(self) -> int:
        state = cache.get(self.key)
        if state is None or state["failures"] < settings.LOGIN_MAX_FAILURES:
            return 0
        return max(1, int(state["end"] - time.time()))

    # ein weiterer Fehlschlag
    def failure(self) -> None:
        state = cache.get(self.key)
        if state is None:
            # ein neues Fenster beginnt
            state = {"failures": 0, "end": time.time() + settings.LOGIN_WINDOW_SECONDS}
        state["failures"] += 1
        # der Schlüssel verschwindet am Ende des Fensters aus dem Cache (timeout, in Sekunden)
        cache.set(self.key, state, timeout=max(1, int(state["end"] - time.time())))

    # ein erfolgreiches Login löscht die Fehlschläge
    def clear(self) -> None:
        cache.delete(self.key)

    Der Limiter zählt die fehlgeschlagenen Versuche eines Clients innerhalb eines festen Zeitfensters: höchstens drei fehlgeschlagene Versuche pro Fenster von 60 Sekunden, gerechnet ab dem ersten Fehlversuch. Jeder Client wird anhand seiner IP-Adresse identifiziert.

    • Zeile 13: der Cache-Schlüssel, spezifisch für den Client: [login.127.0.0.1];
    • Zeilen 16–20: die Anzahl der Sekunden, die gewartet werden muss, wenn der Client blockiert ist (die Zahl der Fehlschläge hat das Maximum erreicht), sonst 0. Der im Cache gespeicherte Zustand ist ein Dictionary: die Anzahl der Fehlschläge und der Endzeitpunkt des Fensters;
    • Zeilen 23–30: ein weiterer Fehlschlag. Gibt es keinen Zustand im Cache, beginnt ein neues Fenster. Der Zustand wird mit einer Lebensdauer neu geschrieben, die am Ende des Fensters abläuft: Der Cache vergisst ihn dann automatisch, und der Client beginnt wieder bei null;
    • Zeilen 33–34: Eine erfolgreiche Anmeldung setzt die Fehlschläge zurück.

    Dieser zur Veranschaulichung geschriebene Limiter hat eine Schwäche: Zwei gleichzeitige Fehlschläge könnten denselben Zustand lesen und nur als einen zählen. Der Cache von [Django] bietet atomare Operationen ([cache.add], das nur schreibt, wenn der Schlüssel nicht existiert, und [cache.incr], das eine Zahl erhöht), die in der Version der Fallstudie verwendet werden. Es gibt auch fertige Bibliotheken ([django-ratelimit], [django-axes]).

# GET: das Formular; POST: das Login, mit Captcha und Begrenzung der Versuche
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return login_page(request)
    login = request.POST.get("login", "")
    # der Limiter DIESES Clients: Seine Fehlschläge werden unter seiner IP-Adresse gezählt
    limiter = Limiter(request.META["REMOTE_ADDR"])
    # 1. eine gesperrte Adresse wird gar nicht erst angehört
    seconds = limiter.wait()
    if seconds > 0:
        return login_page(request, login, f"Too many attempts: try again in {seconds} s.")
    # 2. zuerst das Captcha (billig), danach das Passwort (PBKDF2, teuer)
    if not captchas.verify(request.POST.get("captcha_id", ""), request.POST.get("captcha", "")):
        limiter.failure()
        return login_page(request, login, "The code of the image is incorrect.")
    user = auth.validate(login, request.POST.get("password", ""))
    if user is None:
        limiter.failure()
        return login_page(request, login, "Incorrect login or password.")
    limiter.clear()
    response = redirect("profile")
    response.set_cookie(auth.COOKIE, auth.create_token(user),
                        max_age=settings.JWT_DURATION_MINUTES * 60, httponly=True, samesite="Lax")
    return response
